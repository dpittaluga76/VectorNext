# Working on VectorNext

VectorNext is an original vector database and local document-retrieval system. The repository contains Rust storage/retrieval and TXT/JSON/PDF ingestion, CPU PDF/OCR and model workers, durable jobs, real MiniLM embeddings/reranking, optional local Gemma context generation, source-linked answers, bounded GPU generation priority, and runnable evaluation fixtures. T09 adds the shared API, isolated CPU admission, Compose, CLI and verified offline export/restore. T10 completes development evaluation and a capacity probe. T11 adds a public NASA/USGS comparison, a UTF-8 ingestion repair and a verified real README demo. There is no web UI; T11 exposes ingestion and answer-quality gaps, and broad independently administered quality remains unproven.

## Design discipline

- Explicit user instructions can change the design. Update the documents to reflect those changes.
- Preserve confirmed requirements. Clearly distinguish proposed choices, experiments, and implemented behavior.
- Use the architecture as the implementation reference; tasks and existing code must not silently redefine it.
- Resolve routine implementation details within the requested scope. If a choice materially changes a confirmed requirement, raise the specific conflict rather than inventing a new requirement.
- Build our own vector storage, similarity search, keyword index, and query behavior. General-purpose parsing, numerical, serialization, and model-runtime libraries are allowed.
- Keep model inference outside database transactions. Preserve original evidence separately from generated context and formatted answers.
- Keep all application components containerized and normal operation local. The target has one RTX 4060 with 8 GB VRAM; avoid assuming several large models fit concurrently.

## Verification

T03 storage contracts and durability rules are in [docs/storage.md](docs/storage.md), implemented in `src/`. Run `docker compose build core`, then `docker compose run --rm core` (all storage, search, and diagnostic tests). Format/lint commands are in README.md. Core tests use supplied vectors, no model service or network, and target Linux/Docker; native Windows storage is unsupported. Keep model calls outside transactions. Preserve exact typed values, revision-scoped provenance, immutable embedding identities, and retry semantics.

T04 retrieval is in `src/search/`, specified in [docs/retrieval.md](docs/retrieval.md). `SearchIndex` is immutable and scoped to one committed snapshot/embedding space; build a fresh index for a new generation. Exact cosine, per-field BM25, explicit typed filters, RRF, and conservative source-preserving deduplication are implemented. The [diagnostic report](docs/reports/t04-retrieval.md) uses hand-prepared records and supplied vectors; it is not a model-quality benchmark or T01 holdout run.

T05 ingestion is in `src/ingestion/`, specified in [docs/ingestion.md](docs/ingestion.md). Rust performs deterministic TXT/JSON preparation through a serializable processor contract; the processor never receives a database handle. Jobs use separate atomic checksummed files under the sole writer lock and publish complete revisions with stable batch receipts. Preserve UTF-8 source mappings, exact `record`/`value` attributes, revision-scoped JSON pointers, and actual encoder token budgets. `TestEncoder` is deliberately synthetic and has its own embedding-space identity; do not treat its vectors as semantic quality or reuse its identity for MiniLM. The runnable inspector and disk-volume tests are in [the developer guide](docs/development.md). T06 adds PDF/OCR; T07 connects real models and context policies. Do not rerun GPU benchmarks for parser/storage changes.

The T01 evaluation service is runnable: `docker compose build evals`, `docker compose run --rm evals`, and `docker compose run --rm evals python -m unittest evals.test_validate -v`. Rebuild after editing evaluation files. See evals/README.md for source-location conventions and regeneration rules. Do not report the database application as runnable until it has been implemented and exercised.

T06 PDF/OCR is in `processor/` and `src/ingestion/pdf.rs`, specified in [docs/pdf-ingestion.md](docs/pdf-ingestion.md). Use `compose.processor.yaml` for explicit model setup and offline CPU checks. The processor has no database mount; its versioned artifacts bind source/profile hashes and are validated by Rust before durable stages. Preserve page/box provenance, OCR diagnostics, table header sources, and strict partial-extraction handling. Test captures live in `tests/fixtures/pdf/`; review changed captures against sources instead of treating them as gold. Never regenerate PDFs/labels during tests. See [T06 results](docs/reports/t06-pdf.md).

T02 model setup and measurement commands are in experiments/t02/README.md. Model files live under ignored models/; setup downloads are explicit, and inference stays offline. Read docs/reports/t02-local-models.md before using the candidate models: hardware feasibility passed, but answer correctness remains limited. Reuse its exact embedding-space identity as a baseline, not a hard-coded database restriction. Do not rerun GPU/model benchmarks for unrelated storage or documentation changes.

The larger-model comparison is in docs/reports/t02-gemma4-26b.md. The optional 26B profile uses CPU expert offload. The later docs/reports/t02-status-schema.md records 13/13 exact dev outputs with `--schema-mode status` at temperature 0; citation gaps remain. Legacy schema mode and the E2B base Compose configuration preserve earlier comparisons. T03 needs supplied vectors, not a running generation service.

T07 model integration is in `src/ingestion/context.rs`, `worker.rs`, and `model_worker/`, specified in [docs/model-ingestion.md](docs/model-ingestion.md). `compose.ingestion.yaml` runs the Rust CLI/Python child plus the pinned 26B GPU service. Preserve separate generated annotations, complete context/configuration identities, token budgets, bounded caches, permitted stage mutations, and old job serialization. The Python child has no database handle but shares CLI filesystem permissions. Read [T07 results](docs/reports/t07-model-ingestion.md) before quality claims: annotations can be redundant; the smoke probe is not a quality benchmark.

T08 answering is in `src/answers.rs`, `examples/ask.rs`, and `model_worker/answers.py`; generation admission is in `model_worker/scheduler.py`. Read [the answer contract](docs/answers.md) and [T08 results](docs/reports/t08-answers.md). Keep original questions/history, snapshot generation, source evidence, and exact JSON values authoritative. JSON model output selects a record/pointer with a null placeholder; Rust materializes the source value before validating. Never confuse that placeholder, a supported raw null, an unknown count, and a missing pointer. Prose drafts cannot replace validated fields or become retrieval inputs. Mechanical support does not establish semantics. Preserve bounded queue deadlines, interactive priority, non-preemptive active work, and fail-closed backend uncertainty. Use T09’s shared API for concurrent work; older separate CLIs still contend for the initial writer lock. Do not rerun model benchmarks for unrelated changes.

T09 is in `src/service/`, `src/backup.rs`, `deployment/`, and `compose.app.yaml`. Read [the deployment contract](docs/deployment.md) and [T09 results](docs/reports/t09-deployment.md). The API alone mounts durable storage; the processor has separate bounded interactive/background lanes and no database mount; only the generation service gets GPU access. Keep parsing/inference outside the database mutex. Check capability readiness separately from liveness. Failed jobs need explicit retry; interrupted stages may recompute but publish once. Backups require the exclusive writer lock, exact file/hash manifests and restoration into a new destination. Preserve exact numeric HTTP/client output and existing model/PDF identities. The T09 drill stops/recreates only its dedicated project; do not reuse user data for fresh-volume tests. See README for the quickstart and [the developer guide](docs/development.md) for setup/restore details. Do not rerun GPU quality benchmarks for unrelated changes.

T10 is in `evals/run.py`, `score.py`, `summarize.py`, `requests.py`, the replay/capacity examples and `compose.eval.yaml`. Read [the protocol and amendments](docs/evaluation.md), [results](docs/reports/t10-evaluation.md) and [reproduction guide](evals/README.md). Keep structural context and 30/20/5 answer defaults; T11 confirms losses with two primaries despite their speed advantage. Keyword weights are independent of embedding policy: fully plain retrieval requires structural/generated weights 0/0. Preserve raw body, original source-label and assembled-context metrics separately; generated text is never evidence. The 400-document probe uses supplied vectors and makes no semantic-quality claim. T10 services are stopped, data/caches/captures retained, and the six holdout questions unused. Use fresh capture and database paths for any authorized repeat; do not rerun GPU benchmarks for unrelated changes.

T11 uses `evals/independent/` and `compose.independent.yaml`. Read the [frozen protocol](docs/t11-protocol.md), [pre-query UTF-8 repair amendment](docs/t11-protocol-amendment-01.md), [results](docs/reports/t11-independent.md) and [source/reproduction guide](evals/independent/README.md). The 20 NASA/USGS sources, 28 questions and labels are frozen; never regenerate them during tests or tune on observed comparison results. The runner sends only the separate public request file, isolates `vectornext-t11` on port 8091, preserves ingestion/HTTP failures in denominators and never deletes volumes. Both limits use the same corpus/images. All four blocks completed: five scored 16/28, two 15/28 in each cache pass; retain five. PDF admission, conversational/multi-document selection and structured-answer validation failures remain explicit. Preserve separate source-review exceptions without rewriting gold. All T11 services are stopped; retain volumes, the interrupted attempt and both execution freezes. T12/T13 are proposed follow-ups. The original six T01 holdout questions remain unused.

Fixture validation must never regenerate sources or gold labels automatically. It checks fixture integrity, not retrieval quality or factual entailment. OCR transcriptions need visual review; holdout questions must stay out of model prompts and tuning decisions.

Prioritize tests for persistence and crash recovery, atomic document updates, exact-search correctness, source mapping, structured-data fidelity, and retrieval quality. Format compliance alone does not establish answer correctness. Run checks appropriate to the change and record limitations honestly.
