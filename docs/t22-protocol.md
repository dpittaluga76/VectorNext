# T22 filter profiling protocol

Frozen before production edits, 2026-10-15. Baseline production commit: `c7427f3`. T22 changes only disposable filter execution indexes; T20/T21 scores, sources and volumes remain untouched.

Use the same new `examples/filter_profile.rs` against baseline and optimized code. Copy the stopped T20 v3 fixture volume read-only to a new T22 volume and verify its hashes. The stores contain 401/1,601 documents including the existing sentinel (12,832/51,232 vectors). Query vectors come from the first eight existing synthetic queries per size; no model/quality labels are involved. New capture paths and a manifest bind the query/input files, profiler and production trees.

Eleven fixed scopes: all, 5% document IDs, scalar equality at 0, empty equality at 999, inclusive 0..4 numeric range, NOT equality, OR equalities, document/range conjunction, missing attribute equality, nested-pointer fallback and container-equality fallback. Run with eligibility tracing off and on. Exact response SHA-256 (including all returned rankings, traces and counts) must match across builds, runs and passes for each size/scope/trace/query. The original evaluator remains the semantic reference; tests additionally cover exact values, trust, Boolean logic, budget fallback and revision replacement/removal.

Each release process gets 2 CPUs / 4 GiB, no network/GPU, identical data and inputs. Capture database open/index-build times separately, then first and two warm passes of 176 queries each. Hashing/JSON report serialization occurs outside query timing. Record complete search and existing stage durations plus process RSS/high-water marks. These memory values include the database and other indexes, not just filter indexes. Initial passes are not cold disk-cache measurements.

First capture one baseline profiling run at each size before implementation. After both binaries exist, run baseline/optimized/optimized/baseline in fresh sequential processes at each size; retain the exploratory baseline separately. Summarize first versus warm medians/p95, build cost, memory and all equivalence checks. Fixed input order, shared host load, cache effects and a small number of independent query vectors limit performance generalization. No PostgreSQL rerun or superiority claim follows. Do not tune queries after observing results. Record amendments/failures without overwriting captures.

Index policy: immutable document/media postings plus at most 32 lexicographically selected top-level attribute names; scalar columns only, at most 4,096 distinct values, 16 KiB per key, 1 MiB aggregate canonical key bytes and 1,000,000 attribute posting slots. An incomplete/over-budget column is discarded and falls back to scan. Nested pointers and container comparisons retain the scan evaluator. Numeric keys preserve exact decimal order/equality. Index limits are construction work/memory bounds, not collection admission limits or a byte-exact resident-memory guarantee.

Acceptance: full semantic equivalence, improved targeted scalar-filter timings with build/memory tradeoffs disclosed, existing regressions and Linux format/Clippy passing, documented unsupported paths and isolated reproducible reports. No normal service upgrade, historical rewrite or GPU quality experiment.
