# T08 query, evidence, and answer contract

Design reference: [answer construction](architecture.md#answer-construction-and-validation), [durable answer jobs](architecture.md#durable-answer-jobs-and-fallback) and [local model scheduling](architecture.md#local-models-and-gpu-ownership). This describes the answer library and earlier CLI; T09 exposes the same contract through its [local API](deployment.md). Reads use one immutable committed index. Models run outside database transactions.

T37 wraps this unchanged answer library in [durable Hybrid routing](answer-jobs.md). Each attempt uses one model lease, original question/history/scope and bound revisions. Rust decides fallback only after final validation; forced modes do not cross models. The supported models are repaired NuExtract3 and Gemma 4 12B, with unchanged two-call answering and exact source rules.

T13 retains bounded diagnostics for failed selected JSON-pointer resolution and answer validation. HTTP 400 `answer_rejected` includes the failing phase, requested fields, an explicitly unvalidated draft and selected source previews/locations inside `error.diagnostics`; no top-level answer or formatted result is returned. Exact JSON types are preserved, large drafts/excerpts are explicitly shortened, and no extra inference is performed. Validation and supported-answer rules are unchanged. See [diagnostic limits and usage](reliability.md#inspect-a-rejected-answer).

The request preserves the original question, bounded conversation turns, explicit trusted filters, requested field types/nullability, and optional formatting. Conversation text is appended as search context, never substituted for the question or treated as evidence. Style rewriting occurs only after retrieval/extraction. Overlong questions or histories fail rather than silently dropping constraints. Generated ingestion annotations participate only in configured search fields, never in reranking or answer evidence.

Hybrid retrieval defaults to 30 candidates per branch, fuses up to 20, and reranks with the pinned CPU cross-encoder. Reranker scores are raw logits, not confidence. Oversized pairs fail explicitly. Evidence assembly retains original chunk spans, mandatory ancestor headings/PDF labels, complete JSON records, and optional same-section neighbors. Intersecting bundles merge their original byte intervals, headings, labels and source references; complete record copies deduplicate by document/revision/location. Distinct documents remain distinct. By default, up to five primary candidates plus immediate neighbors fit an exact rendered-prompt budget of 3,328 input tokens, reserving 768 output tokens in a 4,096-token context. Skipped candidates/expansions appear in explain output. Source references may conservatively cover a whole stored source region.

T10 adds explicit `AnswerOptions` for controlled comparisons: `candidates` (1–100 per branch), `rerank_limit` (1–100, at most twice candidates), `primary_limit` (1–20, at most rerank_limit), and `rerank` (boolean). Omitting options preserves 30/20/5 with reranking. Disabling reranking uses the fused order and records a disabled reranker identity; it does not change evidence or validation rules. Limits and the selected options are visible in each answer report. `timings_ms` records monotonic retrieval, CPU/model preparation, evidence assembly, model calls, and validation durations. Application reports also include snapshot/index acquisition and total application time. Nested durations overlap; they must not be added together as wall time.

### Facet coverage (T25, opt-in)

Set `options.evidence_strategy` to `facet_coverage_v1` for field-focused candidate expansion and final selection. Ranked remains the default, and `coverage_v1` remains compatible. This mode accepts passage scope, 1–4 answer fields, reranking enabled, at most 20 reranker candidates and at most five primaries. Unsupported budgets/field counts fail explicitly; fields are never silently omitted. Facets use each field name (underscores become spaces) plus its description, in deterministic field-name order. Empty descriptions use the name alone. Browser automatic field planning supplies the same definitions; no extra generation call, hard filters, answer values or pointer inference is added.

The main query uses the original question plus latest user question for reference resolution. Each facet runs an additional hybrid query with the same immutable index, explicit filter and candidate budgets. Unique keys are merged round-robin, original query first, to the bounded shortlist. General and per-facet cross-encoder scores see original evidence, never generated context. The T24 selector chooses a best eligible passage per facet, reuses an already selected key, excludes heading-only spans and suppresses at least 80% original-body overlap relative to the shorter span union within one document revision. Remaining slots use general rank; exclusions are not relaxed to pad the result.

Full history/question and original bundles still reach extraction. Existing token checks, exact JSON source materialization, actual-record pointer constraints and numeric/quote validation apply. Neighbor expansion is disabled. Context admission may drop planned primaries; it does not silently exceed the generation budget or retry with different evidence. The report preserves the main `retrieval` response; `selection.candidate_searches` holds auxiliary responses, and `candidate_keys` indexes scores and selector decisions. `field_rankings`, `selector`, `planned_primary_keys`, `admitted_primary_keys` and `skipped` distinguish relevance selection from actual supplied context. Requested rerank pair counts include cached requests and do not claim actual model work. Extra query/search time is `facet_candidate_expansion`; extra reranking/selection is `field_coverage_selection`.

This is experimental relevance coverage, not semantic proof or aggregation. Generic field descriptions may produce weak facets; follow-up decomposition quality is not established by a small integration smoke. T24's authored facets and TXT-only literal-label scores are historical evidence, not an end-to-end quality score for this automatic application mode.

The selected model first assesses answerability with a separate 192-token status/reason schema. Only a supported assessment proceeds to field extraction (768-token output limit). This separation addressed a development failure where a detailed proof schema distracted from ambiguity. Both prompts use the same original question/history/evidence and are budgeted with the actual rendered template. This adds latency and is not an independent semantic verifier. Status precedes dependent fields on the wire; within each proof, the evidence ID precedes its source-format-dependent value/quote/pointer branch. Record evidence requires a JSON pointer. Prompts, ordered schema hashes, assessments and usage are audited.

Supported extraction requires every requested field and a source-linked proof for each. Prose proofs must quote supplied evidence exactly and contain the value under the numeric rules below, or the literal string/boolean. For JSON, the model selects an evidence ID and relative pointer, with a required null placeholder instead of transcribing a value. Rust reads the exact source value, checks any caller-specified pointer, and validates the resulting typed proof. This preserves large integers/decimals and prevents transcription from changing null to zero. Record/field selection still requires semantic evaluation. A raw JSON null is allowed only by an explicitly nullable field; missing pointers are not null. These are mechanical support checks, not semantic entailment. Ambiguous/insufficient outcomes have empty fields. Invalid model output fails visibly rather than becoming an unsupported answer. Answer correctness is scored separately from schema and citation checks.

### Numeric prose support (T15)

`src/answers/numeric.rs` accepts the exact serialized numeric spelling, or that spelling with English thousands grouping in the integer part: a first group of one to three digits, then comma-separated groups of exactly three digits. The sign, fraction and exponent spelling stay literal. For example, `3,000` supports integer `3000`, and `-12,345.06789` supports number `-12345.06789`. No floating-point conversion, rounding, unit conversion, blanket punctuation removal or locale inference occurs. The source text, submitted quote and typed answer are never rewritten. Numeric equivalence alone is insufficient: `3.0` does not support integer `3`, and `3e2` does not support `300`.

For each exact occurrence of the quote in the complete supplied `Evidence.text`, validation checks the surrounding characters there, including outside the quote. Thus quote `3` from `Count: 3,000.` fails. A separate standalone occurrence of `3` can support quote `3`; the API does not carry quote offsets. The matched number must lie inside that quote. Identifier/digit fragments, clipped signs, decimals and exponents, malformed grouping, and numeric adjacency through unsupported separators fail closed. English decimal-point/comma-grouping is an explicit convention: comma decimals, Indian grouping, space/apostrophe grouping, fractions, times and ranges are not converted. Adjacent numeric lists separated only by spaces/punctuation may consequently be rejected. Ordinary sentence punctuation, quoted numbers and hyphenated units such as `3-year` remain usable.

A narrow boundary exception recognizes four-digit years after an English named month, day and comma, with optional horizontal space after the comma, such as `Feb. 25,1969` or `February 25, 1969`. Month names/standard abbreviations are case-insensitive; day validity includes Gregorian leap-year rules. The surrounding date can be outside the submitted year-only quote but must be in the supplied evidence. This is not a general date parser. Numeric dates and other locales remain unsupported by this exception.

Checks are limited to supplied evidence, not unseen original bytes outside that passage; OCR quality and semantic field selection still need evaluation. JSON pointer reads, integer/number field types, explicit null/zero/missing behavior, API shapes and storage contracts remain unchanged. Rejected numeric drafts retain the T13 error envelope. See [T15 verification](reports/t15-numeric-proofs.md); historical T14 captures and scores are unchanged.

The range-endpoint extension recognizes exactly two unsigned endpoints in complete supplied source text, separated by `-`, `–`, or horizontal-space-delimited `to`. Endpoints may use literal decimals or valid English comma grouping. Only an entire endpoint inside the exact quote is supported; no interior value, duration or arithmetic is inferred. Full-span outer boundaries reject signs/negative ranges, multi-segment ISO dates/ranges, identifiers, exponents and clipped numeric fragments. Newlines are not range separators. A year-only quote can be supported by its complete source range, just as a named-month date can support its year; this does not establish that the requested field means the start rather than the end. The production image retains its previous behavior until explicitly rebuilt/activated.

An explicit structured-record lookup scans all eligible committed records in the selected index/embedding space under the caller's filter, deduplicates record identity, and reads requested JSON pointers deterministically. Multiple matches are ambiguous, no match or missing fields is insufficient. No LLM runs in this path; callers must supply the record-selection filter and every field's relative pointer. It never counts top-k chunks as records. Corpus aggregation is unsupported in T08 and explicitly rejected; natural-language aggregate wording receives a conservative English guard, not a complete intent parser.

Templates render validated values in caller-specified order. Optional model prose is a separately labeled presentation draft and cannot change search, structured values, or citations. Rust passes exact display literals as strings so Python does not round arbitrary-precision source numbers. A draft missing literal field values or ending in a question is rejected; these checks do not establish semantic faithfulness. The authoritative original question and formatted fields remain available beside it. Rewriting does not drive retrieval or automatically modify conversation state.

Generation is serialized by a bounded priority queue in the GPU container. The llama.cpp backend binds loopback; the internal-facing wrapper is the only normal entry. Waiting interactive requests precede waiting background enrichment; FIFO holds within each class. Active work is not preempted. Queue capacity, wait deadlines, request/output limits, and backend timeout are enforced. A backend timeout poisons generation admission until service restart so a still-running backend request cannot overlap the next one. Health/status requests remain separate from admission. This is an in-memory scheduler; queued work is not durable, and ingestion retries remain owned by Rust jobs.

All model, prompt/schema, reranking, scope, and retrieval settings appear in explain/audit output. No answer cache is introduced. The existing embedding/reranking caches key exact inputs and model identities; committed snapshot generation and evidence revisions remain in the answer trace.

After JSON selection, Rust first verifies the entire materialized candidate against the supplied exact records. A proven explicit null for a non-nullable field becomes `insufficient_evidence` with empty answer fields and an audited `source_null_abstention`; explicitly nullable requests retain supported null. A malformed selection, missing pointer, or wrong type still fails visibly. Source reads are recorded in `json_values_resolved_from_source`. This uses source data, never expected evaluation answers.

Operational bounds: 16 waiting requests (one slot reserved for interactive admission), 30-second queue deadline, 32 HTTP handlers, 4-MiB bodies/replies, 20-second template/tokenizer backend calls and 180-second generation backend calls. Expired queued requests never execute. Admission rejects overload explicitly; priority is not a promise that a request survives a long active generation. Rust bounds each worker call at 420 seconds, or 720 seconds for the two-generation answer operation. Optional prose uses a separate call. Background requests may starve under sustained interactive traffic; durable ingestion owns retry. The wrapper has no public host port or authentication in this local development setup.

The CLI releases its database writer lock immediately after taking a snapshot, before model work. It still cannot acquire that initial snapshot while another CLI holds the writer lock. T09 provides a shared long-running database owner/read path and CPU admission; use its API for concurrent ingestion and answering. The older CLI retains this lock limitation. Complete records or question/history that exceed budgets fail/skip explicitly; there is no silent truncation, exhaustive ambiguity guarantee, broad multilingual quality claim, or corpus aggregation.

## Experimental field coverage (T14)

`AnswerOptions.evidence_strategy` defaults to `ranked`. The opt-in `coverage_v1` requires reranking and at most 20 candidates. It uses the current question plus the latest user turn for retrieval; the answer model still receives the complete original history. This focus can lose an entity supplied only by an assistant turn, so it is a hypothesis to evaluate, not a general conversation resolver.

Each requested field produces a separate CPU rerank query using its name, description and retrieval focus. In sorted field-name order, select each field's best candidate, then its second best; deduplicate keys and cap at `primary_limit`. Fill to two from the general ranking when possible, respecting that cap. Source merging and the prompt budget can reduce actual evidence. Coverage selection retains source headings/table labels but skips unconditional neighbor expansion. It neither searches beyond the existing fused pool nor guarantees all constraints or alternative events are covered. More fields add bounded CPU work (up to the existing 12-field limit).

The report retains the general `ranked` list and adds `selection`: per-field queries/scores/model identity, planned and admitted primary keys, and the neighbor policy. `timings_ms.field_coverage_selection` measures the extra ranking work. The readable workflow includes this stage and its high-level function calls. Source-budget/duplicate exclusions remain visible separately. The default model messages and evidence assembly remain unchanged.

For JSON evidence only, `coverage_v1` builds a catalog of existing scalar/null paths from exact source JSON. The generation schema binds each evidence ID to paths matching the requested type (or raw null); an explicitly supplied pointer must also exist. The visible catalog contains paths rather than values and is included in prompt token counting. Rust still reads and validates the exact source value; a stored null can trigger the existing non-nullable abstention. A missing field does not become a null or zero. Correct type and existence do not establish that a chosen pointer answers the question.

Catalog bounds: 256 scalar/null leaves per record, depth 64, 2,048 UTF-8 bytes per pointer and 32,768 bytes for the complete catalog. Exceeding a bound fails explicitly; there is no silent schema truncation or fallback to unconstrained paths. Empty objects/arrays are not scalar answer fields. Numeric type inspection preserves decimal syntax instead of rounding through Python floats.

### Ranked JSON pointer constraints (T28)

Ranked extraction now enables the same existing worker catalog/schema whenever a JSON record is added to the evidence under consideration. It enables constraints before the actual prompt-token check and restores the previous constraint state if the added record does not fit. The final catalog therefore contains only admitted records, including admitted neighbors. Ranked prose-only messages and the coverage modes retain their previous behavior. Two versus five primary passages changes selection budgets, not pointer validity rules.

Each schema branch binds one evidence ID to paths matching that requested field's type and any explicit pointer; a union of unrelated records' paths is never used. Stored null paths retain the existing Rust non-nullable abstention check. The worker's schema and prompt hashes identify the actual extraction contract. No model call, repair retry, source-value transcription or relaxed Rust proof check is added. Catalog tokens can reduce evidence admission, and grammar/schema work can affect latency. Existing catalog bounds fail explicitly rather than reverting to unconstrained extraction.

These constraints exclude invalid paths from accepted output, but a valid path can still be semantically irrelevant. Missing fields, conflicting records and same-type distractors remain model-quality questions, tested separately from syntactic schema validity. The [T28 evaluation](reports/t28-ranked-pointers.md) completed 208 requests, recovered the T27 regression cases and promoted 12B after its application/hardware gates. This does not establish general semantics or correct abstention on unseen documents. That measured release retained range rejection; the later endpoint extension above preserves rejection of clipped numeric fragments.

The client exposes `ask request.json --evidence-strategy coverage_v1`. At the API, set `options.evidence_strategy` alongside the ordinary request. Omit it to keep ranked five. See the [T14 frozen protocol](t14-protocol.md) and [reproduction guide](../evals/coverage/README.md).
